# 計画：ITスキル・AIスキル向上のための機能改修ロードマップ

## 概要

AI駆動開発（Claude Codeによる仕様駆動開発）が主流となった現在、本リポジトリの機能改修を題材に
ITスキル（設計・実装・テスト・運用）と AIスキル（AIへの指示設計・レビュー・大規模リファクタリングの伴走）を
実践的に伸ばすための改修案を5つ検討し、優先順位付きのロードマップとしてまとめる。

各案は最終的に個別の `docs/plan_<feature-name>.md` に仕様化し、
[docs/plan_ai-spec-driven-development.md](./plan_ai-spec-driven-development.md) の開発フローに従って実装する。

## 改修案 1: 静的解析・型チェック導入と AI 一括修正パイプライン

### 概要

`ruff`（Lint + フォーマット）と `mypy`（型チェック）を導入し、pre-commit フックと CI に組み込む。
導入時に大量に出る既存コードへの指摘は、Claude にカテゴリごとにまとめて修正させる。

### 現状の問題点

- コードスタイル・未使用importなどが目視レビュー頼み
- 型ヒントはあっても検証されておらず、実行時までバグに気づけない

### 学べること

- **ITスキル**: Python の型システム（`Optional`/`Union`/ジェネリクス等）、Lintルールのプロジェクト適用設計、pre-commit の仕組み
- **AIスキル**: 「ruffの指摘をファイル単位でまとめてAIに投げ、差分だけレビューする」という、機械的だが量の多い修正をAIに安全に任せる指示の出し方を学べる。仕様書ではなく "Lint出力" を入力に実装させる初めての練習になる

### 実装方針

| ファイル | 変更種別 | 概要 |
|---------|---------|------|
| `backend/requirements.txt` | 変更 | `ruff`, `mypy` を追加（開発用は `requirements-dev.txt` に分離検討） |
| `backend/pyproject.toml`（新規） | 追加 | ruff/mypy の設定（対象ディレクトリ、除外、厳しさレベル） |
| `.pre-commit-config.yaml`（新規） | 追加 | ruff/mypy をコミット前フックに登録 |
| `.github/workflows/test.yml` | 変更 | `pytest` の前に `ruff check` / `mypy` のステップを追加 |

### 進め方（段階導入）

1. まず ruff のみ導入し、`--fix` で自動修正できる指摘を一括適用（AIレビューで差分確認）
2. mypy は `--strict` ではなく緩めの設定から開始し、型エラーをモジュール単位でAIに修正依頼
3. CI をブロッキングにするのは指摘がゼロになってから

### 確認事項（未決事項）

1. mypy の厳格度（`disallow_untyped_defs` を最初から有効にするか）
2. ruff のルールセット（`E,F,I` 程度に絞るか、`ALL` に近づけるか）

## 改修案 2: フロントエンドE2Eテスト導入（テストピラミッドの完成）

### 概要

`TEST_PLAN.md` はバックエンドのユニット〜結合テスト＋CI組み込みまで完了しているが、
フロントエンド（Jinja2 + Alpine.js の画面操作）は一切自動検証されていない。
Playwright で主要画面（取引入力、ダッシュボード、レポート）の E2E テストを追加する。

### 現状の問題点

- 画面の動作確認は `/verify` スキルによる手動確認のみで、リグレッションを機械的に検知できない
- Alpine.js の `x-data` 内ロジック（親カテゴリ→子カテゴリ取得等）はユニットテスト不可能な構造

### 学べること

- **ITスキル**: Playwright/ブラウザ自動化、E2Eテストの設計（何をE2Eで見て何をユニットに任せるか）、CIでのヘッドレスブラウザ実行
- **AIスキル**: `docs/specs/` の仕様書（例: `spec_transactions.md`）を入力に、AIへ「この仕様のUI動作確認手順をPlaywrightテストとして書いて」と依頼する、**仕様書→テストコードのAI生成**を実践できる（`plan_ai-spec-driven-development.md` Phase 3 で構想されている「完了条件をテストケースとして記述」の発展形）

### 実装方針

| ファイル | 変更種別 | 概要 |
|---------|---------|------|
| `frontend/tests/`（新規） | 追加 | Playwright テストディレクトリ |
| `frontend/package.json`（新規） | 追加 | `@playwright/test` 依存追加 |
| `.github/workflows/test.yml` | 変更 | `docker compose up` 後に Playwright ジョブを追加 |
| `docs/plan_frontend-e2e-testing.md`（新規） | 追加 | 対象画面・シナリオの仕様書 |

### 対象候補シナリオ

- 取引入力（`/transactions/new`）: 親カテゴリ選択→直近10件表示→コピー→登録
- ダッシュボード: 当月収支・円グラフの表示、今日の支払いパターンバナー
- レポート月次集計: 親クリックで子展開

### 確認事項（未決事項）

1. CIでDockerを起動してE2Eを回すか、SQLiteなど軽量構成で妥協するか（起動コストとのトレードオフ）
2. 対象を主要3画面に絞るか、全画面をカバーするか（初回は3画面に絞ることを推奨）

## 改修案 3: DBアクセスの非同期化（SQLAlchemy Async 化）

### 概要

`database.py` の同期 `Session`/`create_engine` を `AsyncSession`/`create_async_engine` + `asyncpg` に置き換え、
FastAPI のルーターも `async def` + `await db.execute(...)` へ移行する。

### 現状の問題点

- 現状 `async def` のルーターがあっても内部は同期 `Session` を使っており、非同期の恩恵を受けていない（同期I/Oがイベントループをブロックする）
- レポート系（月次集計・年次集計）など重いクエリがある画面で将来的にスループットの課題になりうる

### 学べること

- **ITスキル**: Python非同期I/O（`asyncio`/`async`/`await`）の実践、コネクションプール設定、Before/Afterでの性能計測（負荷試験の基礎）
- **AIスキル**: 影響範囲が広い機械的リファクタリング（`crud/` 全ファイルの書き換え）をAIに安全にやらせるための、**特性テスト（characterization test）を先に固めてから着手する**という進め方を体得できる。既存のpytest結合テストが「非同期化しても壊れていないことを保証する回帰防止網」として機能する

### 実装方針

| ファイル | 変更種別 | 概要 |
|---------|---------|------|
| `backend/app/database.py` | 変更 | `create_async_engine` + `AsyncSession` に変更 |
| `backend/app/crud/*.py` | 変更 | 全CRUD関数を `async def` + `await` に書き換え |
| `backend/app/routers/*.py` | 変更 | `Depends(get_db)` の型を `AsyncSession` に変更 |
| `backend/requirements.txt` | 変更 | `asyncpg` を追加（`psycopg2-binary` は移行完了まで併存） |
| `backend/tests/conftest.py` | 変更 | テストDBフィクスチャを非同期対応に変更 |

### 進め方（段階導入・最も規模が大きいためロードマップの最後に配置）

1. 改修案1（型チェック）・改修案2（テストピラミッド完成）を先に終わらせ、回帰防止網を強化してから着手
2. まず1つのルーター（例: `dashboard`）だけ非同期化し、パターンを確立
3. 確立したパターンをAIに横展開させ、人間は差分レビューに専念する

### 確認事項（未決事項）

1. `psycopg2-binary` を残すか完全に `asyncpg` へ移行するか（Alembicは同期接続のままで良いか）
2. 非同期化の効果測定方法（レポート系エンドポイントのレスポンスタイム計測をどう行うか）

## 改修案 4: 可観測性強化（構造化ロギング＋AI活用の障害調査ワークフロー）

### 概要

FastAPI のミドルウェアでリクエストID付き構造化ログ（JSON形式）を出力し、
`docker compose logs` から障害調査しやすい形に整える。あわせて、ログをAIに渡して根本原因分析させる
運用フローを確立する。

### 現状の問題点

- 現状のログは Uvicorn 標準出力のみで、どのリクエストがどのエラーを起こしたか追跡しづらい
- 障害調査が「勘」に頼りがちで、再現手順の言語化が弱い

### 学べること

- **ITスキル**: 構造化ロギング設計（`structlog` 等）、リクエストIDによるトレーシング、ログレベル設計
- **AIスキル**: 「エラーログを貼ってAIに原因調査させる」際に、**どの情報を渡せばAIが正確に原因を特定できるか**（リクエストID・スタックトレース・直前のクエリなど）を試行錯誤し、効果的なデバッグプロンプトのパターンを確立できる

### 実装方針

| ファイル | 変更種別 | 概要 |
|---------|---------|------|
| `backend/requirements.txt` | 変更 | `structlog` を追加 |
| `backend/app/main.py` | 変更 | リクエストID付与ミドルウェア、例外ハンドラでのログ出力を追加 |
| `backend/app/logging_config.py`（新規） | 追加 | 構造化ログの初期化設定 |
| `CLAUDE.md` | 変更 | 「障害調査時はこのログ形式をAIに渡す」運用ルールを追記 |

### 確認事項（未決事項）

1. ログの保存先（標準出力のみで良いか、ファイル/外部サービスへの転送まで含めるか）
2. 個人情報（取引金額・メモ等）をログに含めない設計（マスキング方針）

## 改修案 5: AIコードレビューのCI組み込み＋依存脆弱性スキャン

### 概要

`docs/plan_ai-spec-driven-development.md` の **Phase 2（レビュー自動化）** をそのまま実行する。
PR作成時にCI上で `/code-review` 相当のチェックを走らせ、あわせて `pip-audit`（依存脆弱性スキャン）を
`.github/workflows/test.yml` に追加する。

### 現状の問題点

- Phase 1（仕様書先行）は定着しているが、Phase 2（レビュー自動化）が未着手のまま放置されている
- 依存パッケージの脆弱性チェックが一切ない（`requirements.txt` のバージョンが安全か検証されていない）

### 学べること

- **ITスキル**: CI/CDへのセキュリティゲート組み込み、サプライチェーンセキュリティ（SCA: Software Composition Analysis）の基礎
- **AIスキル**: 「このプロジェクト固有のレビュー観点（CLAUDE.mdのJST/サブクエリ/tojsonルール等）をAIに機械的にチェックさせるにはどうプロンプト/スキルを設計すべきか」を、既存の `/code-review` スキルを土台に実践できる。**最も既存資産（仕様駆動開発フレームワーク）と直結し、最小の追加実装で着手できる案**

### 実装方針

| ファイル | 変更種別 | 概要 |
|---------|---------|------|
| `.github/workflows/test.yml` | 変更 | `pip-audit` ステップを追加（脆弱性検出時はCIを失敗させる） |
| `.github/pull_request_template.md`（新規） | 追加 | Phase 2 で予告されていたPRテンプレートへの正式移行 |
| `docs/plan_ai-spec-driven-development.md` | 変更 | Phase 2 完了を反映（付録の対応表を更新） |

### 確認事項（未決事項）

1. AIコードレビューをCI上で自動実行するか（コスト・実行時間）、それとも「PR作成時に人間が `/code-review` を手動起動する運用ルール化」に留めるか
2. `pip-audit` で検出された既存の脆弱性への対応方針（即修正 or 別issue化）

## 推奨実施順序（ロードマップ）

```
Step 1: 改修案5（AIレビュー組み込み＋脆弱性スキャン）
        └─ 既存フレームワークの続きなので着手障壁が最も低い。以降の改修のレビュー品質も底上げされる

Step 2: 改修案1（静的解析・型チェック導入）
        └─ 型チェックがあると Step 4 の非同期化リファクタリングの安全性が上がる

Step 3: 改修案4（可観測性強化）
        └─ ログ基盤があると以降の改修の動作確認・障害調査が効率化する

Step 4: 改修案2（フロントエンドE2Eテスト導入）
        └─ 回帰防止網をバックエンド・フロントエンド双方で固める

Step 5: 改修案3（DBアクセスの非同期化）
        └─ 影響範囲が最も広いため、Step 1〜4で固めた型チェック・テスト・ログを
           安全網として使いながら最後に着手する
```

各ステップ着手時は、本ドキュメントの該当セクションをもとに
`docs/plan_<feature-name>.md` として個別の仕様書を作成し、
[docs/plan_ai-spec-driven-development.md](./plan_ai-spec-driven-development.md) の開発フロー（仕様書レビュー→AI実装→実装レビュー→commit/PR）に従うこと。
