# 計画：AI仕様駆動開発フレームワーク

## 概要

Claude Code（AI）を活用して、仕様書を起点とした開発サイクルを確立する。
仕様を先に書き、AIがそれを実装し、人間がレビュー・承認するワークフローにより、
実装品質の安定化・手戻り削減・ナレッジの蓄積を目指す。

---

## AI仕様駆動開発とは

従来の「コードを書いてから説明する」開発に対し、「仕様を書いてからAIに実装させる」開発。

```
[従来]  要件 → 実装 → ドキュメント（後付け）
[AI駆動] 要件 → 仕様書 → AI実装 → レビュー → commit/PR
```

### メリット

| メリット | 説明 |
|--------|------|
| 設計の明確化 | 実装前に問題を発見できる（仕様書レビュー段階） |
| AI指示の精度向上 | 仕様書が詳細なほどAIの実装精度が上がる |
| ナレッジ蓄積 | 仕様書がそのままドキュメントになる |
| レビュー効率化 | 仕様と実装の差分を確認するだけでよい |
| 再現性 | 同じ仕様書から同じ実装を再現できる |

---

## 開発フロー

```
1. フィーチャー計画
   └─ 要件・目的を明確にする

2. 仕様書作成（docs/plan_<feature-name>.md）
   └─ 仕様書テンプレートに従って記載

3. 仕様書レビュー（人間）
   └─ 実装前に設計の問題点を洗い出す
   └─ 必要に応じて修正 → 再レビュー

4. AIへの実装依頼
   └─ 「docs/plan_<feature-name>.md の仕様に従って実装してください」

5. AI実装レビュー（人間）
   └─ 仕様との差分確認
   └─ 動作確認（/verify スキルで画面動作を手動確認）
   └─ 仕様書の不備が判明した場合は Step 2 に戻って仕様書を修正してから再依頼
   └─ 実装上の問題なら修正指示 → 再実装

6. commit & PR
   └─ コミット順序はブランチ・コミット規約に従う（仕様書→実装の2コミット分割）
   └─ PR本文に仕様書へのリンクを記載
```

## 仕様書の品質基準

AIが仕様書から正確に実装できるよう、以下の基準を満たすこと。

### 必須項目

| 項目 | チェックポイント |
|------|----------------|
| 目的が明確 | 「なぜ変更するか」が1文で言える |
| 変更ファイルが特定されている | パスが具体的に記載されている |
| 完了条件が検証可能 | 「〜できること」「〜が表示されること」など客観的な基準 |
| 既存コードへの影響が考慮されている | 変更が他機能に与える影響を記載 |

### 推奨事項

| 項目 | 理由 |
|------|------|
| コードスニペットを含める | AIが実装イメージを掴みやすくなる |
| NG例を書く | 「〜しないこと」を明示するとミスが減る |
| CLAUDE.md の関連ルールを参照 | プロジェクト固有のルールをAIに意識させる |

### 避けるべき書き方

| 避けるべき | 理由 | 代替 |
|-----------|------|------|
| 「いい感じにする」 | AIが解釈できない | 具体的な変更内容を記載 |
| 「適切に処理する」 | 基準が曖昧 | 具体的な条件分岐を記載 |
| ファイルパスなし | AIが対象を特定できない | `backend/app/crud/pattern.py:_to_dict()` のように指定 |

## AIへの依頼方法

### 標準依頼文

```
docs/plan_<feature-name>.md の仕様に従って実装してください。
```

### 実装後の確認依頼

```
実装を完了したら、以下を確認してください：
1. 仕様書の完了条件をすべて満たしているか
2. CLAUDE.md の注意点に違反していないか
3. 既存テストが通るか（該当する場合）
```

### 問題が見つかった場合の修正依頼

```
<問題の説明>が想定と異なります。
仕様書の「<該当セクション>」に従って修正してください。
```

## レビューチェックリスト

### 仕様書レビュー（実装前）

- [ ] 「なぜ変更するか」が1文で言えるか（目的が明確）
- [ ] 変更対象ファイルが具体的なパスで特定されているか
- [ ] 完了条件が検証可能か（「〜できること」「〜が表示されること」など）
- [ ] 既存コードへの影響が考慮されているか（他機能・他ファイルへの波及）
- [ ] CLAUDE.md の制約と矛盾していないか
- [ ] 確認事項（未決事項）が明記されているか

### 実装レビュー（AI実装後）

- [ ] 仕様書の完了条件をすべて満たしているか
- [ ] 変更対象外のファイルが意図せず変更されていないか
- [ ] CLAUDE.md の注意点（JST、サブクエリ、tojson等）に違反していないか
- [ ] `/verify` スキルで画面動作を手動確認済みか
- [ ] 不要なコメント・デバッグコードが含まれていないか

## ブランチ・コミット規約

### ブランチ命名

```
feature/<feature-name>   # 新機能
fix/<issue-name>         # バグ修正
docs/<doc-name>          # ドキュメントのみ
```

### コミット順序

```
1. docs: 仕様書を追加（plan_<feature-name>.md）
2. feat/fix: 実装を追加（仕様書に従った変更）
```

### PRテンプレート

PR作成時は以下の形式を使う（`.github/pull_request_template.md` に移行済み。下記はレビュー項目を除いた基本形）。

```markdown
## 概要
<1〜3行で変更内容>

## 仕様書
docs/plan_<feature-name>.md

## 完了条件チェック
- [ ] <完了条件1>
- [ ] <完了条件2>

## テスト方法
<動作確認手順>
```

## 本プロジェクト固有のルール

仕様書・実装時に CLAUDE.md の「実装上の注意点」セクションを必ず参照すること。
**CLAUDE.md が正とする。** 以下は代表的なルールの抜粋にすぎない。

| ルール | 場面 |
|--------|------|
| カテゴリ検索はサブクエリを使う（JOINしない） | トランザクション一覧の絞り込み実装時 |
| 日付は `jst.py` の `today_jst()` / `now_jst()` を使う | 日付計算が含まれる実装時 |
| Jinja2 の JSON 埋め込みはシングルクォート属性 | テンプレートへのデータ埋め込み時 |
| `date`/`datetime` はテンプレートへ渡す前に `str()` 変換 | バックエンドからテンプレートへ日付を渡す時 |

## 段階的導入計画

本フレームワークは段階的に導入する。

### Phase 1（即時適用）: 仕様書先行

- 新機能・バグ修正の前に必ず `docs/plan_<feature-name>.md` を作成する
- 既存の `docs/` ディレクトリにそのまま格納

### Phase 2: レビュー自動化（一部完了）

- [x] PRテンプレートを `.github/pull_request_template.md` に移行（2026-10-12、[ADR-0005](adr/0005-ci-dependency-audit-and-ai-review-workflow.md)）。「`/code-review` 実行済み」のチェック項目を追加
- [x] `/code-review` による実装レビューを、PR 作成前に人間が手動で起動する運用ルールとして CLAUDE.md に明記
- [x] 依存脆弱性スキャン（`pip-audit`）を CI にブロッキングで追加
- [ ] ブランチ命名規約を CLAUDE.md に追記し、AI が自動で参照できるようにする（本文書の「ブランチ命名」を CLAUDE.md へ転記する作業が未了）
- 見送り: AI コードレビューの CI 自動実行（`claude-code-action` 等）。`ANTHROPIC_API_KEY` の管理と API コストの基盤がなく、個人開発規模では投資対効果が低いため（[ADR-0005](adr/0005-ci-dependency-audit-and-ai-review-workflow.md) 決定3）。基盤が整った段階で別 ADR として再検討する

### Phase 3（将来）: 自動テスト整備

- 完了条件をテストケースとして記述（pytest / テストファイル追加）
- テストでバックエンドロジックを自動検証（画面確認は Phase 1 より /verify で継続）

## 付録：既存計画書との対応

本プロジェクトの既存計画書（`docs/plan_*.md`）の対応状況は以下のとおり。
新規仕様書を作成する際は既存計画書をそのまま流用せず、テンプレート（本文書）から始めること。

| 計画書 | 足りている点 | 不足している点 |
|--------|------------|--------------|
| plan_pattern-list-design-improvement.md | 現状の問題点、変更ファイル一覧、コードスニペット、実装上の注意点、確認事項 | 完了条件（チェックリスト形式） |
| plan_pattern-enhance-and-quick-entry.md | 変更ファイル一覧、コードスニペット、確認事項 | 現状の問題点、実装上の注意点、完了条件（チェックリスト形式） |
