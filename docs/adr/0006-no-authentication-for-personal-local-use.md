# ADR-0006: 認証を導入せず、個人利用・ローカル稼働を前提とする

## ステータス

採用（Accepted）— 2026-10-12。初期実装時（2026-04）から続く設計判断を、事後に ADR として記録したもの（遡及 ADR）

---

## コンテキスト

### 現状の実装

このアプリには、認証・認可・ユーザーの概念がない。

- `backend/app/main.py` に認証系のミドルウェア・依存関係は登録されていない。全ルーター（`/api/v1/*` と HTML ページ）が無認証で公開されている
- `backend/app/config.py` に `secret_key` 設定があり、`.env.example` と `docker-compose.yml` にも `SECRET_KEY` が渡されるが、アプリのコードからは参照されていない（セッション・署名には未使用）
- DB のテーブル（`transactions`・`accounts`・`categories` など）に `user_id` に相当する列はない。データはすべて「1世帯分」として扱われる
- [DESIGN.md](../../DESIGN.md) の API エンドポイント一覧の「認証」列は、全行が `-`（なし）
- `docker-compose.yml` は、当初 backend を `8080:8000`、DB を `5439:5432` で公開していた。ホスト側の IP を指定していないため、Docker の既定動作で**ホストの全ネットワークインターフェースに公開されていた**（本 ADR の決定3で `127.0.0.1` に限定した）

### 認証がないことの影響が大きいエンドポイント

| エンドポイント | 内容 |
|---|---|
| `POST /api/v1/backup/restore` | アップロードされた `.sql` を `psql` で DB 所有者として実行する。到達できる人は DB に対して任意の SQL を実行できる |
| `POST /api/v1/backup/dump` | 全取引の `pg_dump` をダウンロードできる |
| `DELETE /api/v1/transactions/{id}` ほか各 CRUD | 取引・口座・カテゴリの更新・削除 |
| `POST /api/v1/import/upload` | `Actual.TXT` の取り込み |

### 課題

1. 認証がないこと自体は、個人用ツールとしては合理的だが、それが**意図した判断なのか、未実装なのか**がリポジトリから読み取れない
2. 認証がない前提が成り立つ条件（誰が・どこから使うか）と、その前提が崩れたときの変更範囲が文書化されていない
3. `SECRET_KEY` が設定項目として存在するため、読む人に「認証やセッションが実装済み」という誤解を与えうる

---

## 決定

### 1. 認証を導入しない

このアプリは **1世帯・1台のマシン上で Docker Compose により動かす個人用ツール**として扱い、認証機構は導入しない。

想定する利用形態（この前提を満たす間は、認証を入れない判断が成り立つ）:

| 前提 | 内容 |
|---|---|
| 利用者 | 本人（および同居の家族）。データの閲覧・変更を許してよい人だけがアプリに到達できる |
| 稼働場所 | 本人が管理するマシン上の Docker Compose。インターネットに公開しない |
| データ | 家計の取引データ。他人に見せない前提だが、ユーザーごとの権限分離は不要 |

理由:

- 利用者が1人（1世帯）なら、アプリ内の認証は「ネットワークに到達できる人 = 使ってよい人」という前提の上に重ねる二重のゲートになり、得られる保護に対して実装・運用コスト（ログイン画面、パスワード管理、セッション、全テストの認証対応）が見合わない
- 認証を入れても、データの機密性は「マシンとネットワークの管理」に依存する点は変わらない（`.env` の `DB_PASSWORD` や DB ダンプのファイルも同じマシン上にある）
- 機能開発を、取引入力・集計・パターン管理といった家計簿としての価値に集中できる

### 2. `SECRET_KEY` は未使用であることを明記する

`SECRET_KEY` はセッション等の実装を見越して残されている設定であり、現時点では何にも使われていない。認証が導入された時点で意味を持つ。

### 3. ポートを `127.0.0.1` に限定し、同一マシンからのみ到達できるようにする

`docker-compose.yml` の `ports` を `127.0.0.1:8080:8000`（backend）・`127.0.0.1:5439:5432`（DB）に変更する。認証を入れない前提（利用者だけが到達できる）を、アプリではなく**構成で担保する**。

- 利用者（本人）が、アプリを起動した端末からしか使わないことを確認した上での決定（2026-10-12）
- LAN 上の他の端末（スマートフォン、来客の端末、IoT 機器）からは到達できなくなる
- 同一マシンからの利用（`http://localhost:8080`）と、`docker compose exec` による DB 操作には影響しない

### 4. 前提が崩れる条件を、再検討のトリガーとして定める

次のいずれかに当てはまる場合は、本 ADR を見直し、下記「入れる場合の変更点」に従って認証を導入する。

- 起動したマシン以外（スマートフォンなど）から使いたい。`ports` の `127.0.0.1:` を外す場合は、同じネットワーク上の誰でも到達できるようになるため、先にリバースプロキシ（代替案 B）か認証（代替案 A）を入れる
- 自宅 LAN の外（インターネット、クラウド上のサーバー）から到達できるようにする
- 家族以外の第三者がアクセスできるネットワークで動かす（共有マシン、公共のネットワークなど）
- 複数人で、それぞれ別の家計として使う（マルチユーザー化）
- バックアップ・リストア機能（`/backup`）を、信頼できない環境に出す

## 検討した代替案

### 代替案A: アプリ内に単一パスワードのログインを実装する

- 内容: ログイン画面とセッション Cookie（Starlette の `SessionMiddleware`）を実装し、全ルーターに認証依存関係を付ける。パスワードは環境変数のハッシュ値で持つ
- 長所: 外部コンポーネントなしで完結する。`SECRET_KEY` を活かせる
- 短所: ログイン画面、CSRF 対策（フォーム送信と `fetch` による JSON 送信の両方）、全テストの認証対応が必要。1人用の用途に対して実装範囲が広い
- → **見送り**（再検討のトリガーに該当した場合の第一候補。後述）

### 代替案B: リバースプロキシで Basic 認証を掛ける

- 内容: Caddy や nginx を前段に置き、Basic 認証と TLS を担わせる。アプリのコードは変更しない
- 長所: アプリの変更がなく、テストにも影響しない。外部公開する場合に必要な TLS も同時に解決できる
- 短所: コンテナが1つ増える。アプリ側ではユーザーを識別できない
- → **見送り**。外部から到達させたいだけなら、代替案 A より先にこちらを選ぶ

### 代替案C: Google OAuth 等の外部 IdP を使う

- 内容: ID トークンの検証と許可メールアドレスの照合を行う
- 長所: パスワードを自前で持たない。許可リスト方式で単一ユーザーに限定できる
- 短所: 外部サービスの設定（クライアント ID、リダイレクト URI）が必要で、ローカル稼働の個人ツールには過剰
- → **見送り**

### 代替案D: ポートを `127.0.0.1` にバインドして、同一マシンからのみ到達可能にする

- 内容: `docker-compose.yml` の `ports` を `127.0.0.1:8080:8000` / `127.0.0.1:5439:5432` にする
- 長所: コード変更なしで、LAN 上の他の端末から到達できなくなる。認証を入れない前提を、構成で担保できる
- 短所: スマートフォンなど同一マシン以外の端末から使えなくなる
- → **採用**（決定3）。利用者が起動した端末からしか使わないことを確認したため

## 認証を導入する場合の変更点（代替案 A の場合）

マルチユーザー化を伴わない、単一ユーザーのログインを想定する。

| 対象 | 変更内容 |
|---|---|
| `backend/app/config.py` | `app_password_hash`（パスワードのハッシュ値）を追加。`secret_key` の既定値 `dev-secret-key` を廃止し、未設定なら起動を失敗させる |
| `backend/app/main.py` | `SessionMiddleware`（`secret_key` を使用）を登録。ログイン前のアクセスを `/login` へリダイレクトする依存関係を、API ルーターと HTML ルーターの両方に付ける |
| `backend/app/routers/auth.py`（新規） | `GET /login`、`POST /login`、`POST /logout` |
| `backend/app/templates/login.html`（新規） | ログイン画面 |
| `backend/app/templates/base.html` | ログアウト操作を追加 |
| CSRF 対策 | 状態を変更する `POST` / `PUT` / `DELETE` が対象。取引入力は `fetch` + JSON 送信のため、Cookie の `SameSite=Lax` 以上の設定と、必要に応じてヘッダートークンの検証を行う |
| `backend/tests/conftest.py` | `api_client` で認証依存関係を上書きし、既存の 390 件が認証なしで通るようにする。認証自体のテスト（未ログインで 401 / リダイレクト、ログイン成功・失敗）を追加する |
| `docker-compose.yml` / `.env.example` | `APP_PASSWORD_HASH` を追加 |
| `docs/specs/` | 認証の仕様書を追加し、DESIGN.md の「認証」列を更新する |

マルチユーザー化（複数世帯が別々のデータを持つ）は、上記に加えて `transactions`・`accounts`・`categories` など全テーブルへの `user_id` 追加と Alembic マイグレーション、全クエリへの絞り込み条件の追加が必要になる。認証とは別の大きな変更であり、本 ADR の範囲外とする。

## 影響・注意点

- **ポートは `127.0.0.1` に限定している**: 同じネットワーク上の他の端末からは、アプリにも DB（5439）にも到達できない。ただし、この制限は `docker-compose.yml` の記述に依存する。`ports` からアドレス指定を取り除く、または `docker-compose.override.yml` 等で上書きすると、全インターフェースに公開される
- **同一マシン上の他のプロセス・ユーザーからは到達できる**: `127.0.0.1` への限定は、同じマシンを複数人で使う場合の保護にはならない
- **`/backup/restore` が最も影響が大きい**: 到達できる人は任意の SQL を実行できる。認証を入れない判断は、この機能が信頼できるネットワーク内にしかないことを前提にしている
- **`SECRET_KEY` と `DEBUG` は現状どちらも動作に影響しない**: `settings.debug` もコードからは参照されていない。公開する場合は「`DEBUG=false` にすれば安全」とは考えず、認証の有無そのものを見直す
- **`Actual.TXT` と DB ダンプの扱い**: 認証の有無にかかわらず、実データを含むファイルはリポジトリにコミットしない（`.gitignore` の対象。`Actual.TXT` の履歴混入なしは確認済み）
- **このアプリを公開デモに使う場合**: 実データではなく合成データを使うこと。認証なしのまま外部公開しない
